# ADR 0004 — Operations store: `node:sqlite`, one owner, an append-only ledger

**Status:** Accepted for R0 (FND-01, FND-02) on 12 November 2026; redaction and schema 2 added for FND-06 the same day. Revisit if `node:sqlite` changes incompatibly or the supported Node range drops below 22.13.

## Context

Every operations feature (Autofill answers, Auto Apply attempts, Inbox messages, contacts, interviews, strategy metrics) needs durable records that survive a restart, do not double-apply a retried request, and do not let two writers overwrite each other. The existing recovery sessions are JSON files ([local persistence](local-persistence.md)), which are written whole and cannot express per-record revisions or an event history.

The plan asked for a packaging spike: `node:sqlite` if the supported runtime matrix allows it, otherwise a maintained binding chosen through an ADR.

Evidence, checked on 12 November 2026:

- The root `engines` range is `^22.22.3 || ^24.15.0 || >=26`. `node:sqlite` is available without a flag from Node 22.13, so every supported version has it. CI runs `npm test` on Node 24 (`test-and-build`) and Node 22 (`Node 22 compatibility`).
- It needs no native module. The macOS and Windows package smoke jobs and the preview archive therefore need nothing new, unlike `better-sqlite3`, which ships prebuilt binaries per platform and Node ABI.
- It is still marked experimental and prints an `ExperimentalWarning` on first use.

## Decision

1. **Storage:** one SQLite file at `<REBOUNDOPS_DATA_DIR>/operations/operations.sqlite`, opened through `node:sqlite`. Everything that touches `node:sqlite` stays in `apps/api/src/operations/store.ts`, so a different binding is a local change.
2. **One owner:** the connection takes SQLite's `EXCLUSIVE` lock at open and keeps it (`locking_mode = EXCLUSIVE`, WAL journal). A second process gets `OperationsStoreLockedError`. The OS releases the lock if the owner crashes.
3. **Ledger:** `operation_events` is append-only, except for redaction (item 10). Each event has a caller-chosen UUID (idempotency), an expected revision (optimistic concurrency, a 409 at the HTTP layer), separate event and ingestion times, a source, and a JSON payload (JSON values only) capped at 64 KiB. `operation_entities` holds each record's current revision. Contracts: `OperationEventInputSchema` in `@reboundops/contracts`.
4. **Batches** (`appendEvents`) are all-or-nothing, for imports.
5. **Migrations** are forward-only, numbered with `PRAGMA user_version`, and applied in one transaction. An existing store is first copied with `VACUUM INTO` to `operations.sqlite.pre-v<N>-<timestamp>.bak`. A store with a newer schema than the code knows is refused, never downgraded. A backup is one self-contained file with no WAL. To restore: stop ReboundOps; move `operations.sqlite` together with any `operations.sqlite-wal` and `operations.sqlite-shm` into another folder, keeping the three as a set; then copy the chosen backup to `operations.sqlite`. Never leave an old `-wal` or `-shm` file beside a restored backup: SQLite would apply it to the wrong database, which can lose data or corrupt it.
6. **HTTP** (`apps/api/src/operations/routes.ts`): `GET /api/operations/status`; `POST /api/operations/events` with `{ events: [...] }` (1–100, atomic; `201` when anything was appended, `200` for a pure retry); `GET /api/operations/entities/:entityType/:entityId/events`. Errors: `400 INVALID_REQUEST` with the failing path, `400 INVALID_REQUEST` at path `type` for `record.redacted`, which only the store writes, `404 OPERATIONS_DISABLED` while every flag is off, `409 STALE_REVISION` (with expected and current revision), `409 EVENT_ID_REUSED`, `413 EVENT_PAYLOAD_TOO_LARGE` (one event's payload over 64 KiB), `413` with Fastify's code `FST_ERR_CTP_BODY_TOO_LARGE` (a request body over the API's 128 KiB limit, refused before the route runs, so a large batch must be split), `503` when the store is not configured, locked or newer. These generic routes are the base for each feature's own validated routes.
7. **Legacy tracker import** (FND-03, `apps/api/src/operations/legacy-tracker.ts`): `POST /api/operations/imports/legacy-tracker` with `{ markdown, sourceLabel, dryRun }` (text up to 2 MiB after JSON decoding; the body limit allows for JSON escaping). The caller sends the text of the engine's `data/applications.md`; the API never opens or changes the file, and the report records its SHA-256. A dry run appends no events. Before the first real import it plans against an empty ledger and does not create the store. Once a store exists, a dry run opens it like any other request, so opening can still tighten file permissions and apply a pending migration (after its backup).
   - Columns are mapped by header name with the engine's alias table, falling back to the engine's fixed order. `apps/api/tests/legacy-tracker-parity.test.mjs` holds this reader to `engine/tracker-parse.mjs` (same aliases, fallback and rows), because the preview package does not ship `engine/`.
   - Row `#` maps to the application `legacy-<#>`. Event ids derive from the row's content and the record's revision, so importing the same file again writes nothing. A changed row adds an `application.legacy_updated` event; the earlier event stays. An imported row's event time is its Date cell; an update's is the import time.
   - Two checks are stricter than the engine, so a row is held rather than imported wrong: row width counts every header column, recognised or not, and `#` must be a safe whole number (the engine reads `12a` as 12).
   - Quarantined, with line and reason, and never written: rows with too few cells, a `#` that is not a safe whole number, an invalid date, no company or role, a `#` used twice, a `#` that was imported before with a different company or role, or a row too large for one event (over 64 KiB, usually long notes), so one row never fails the whole atomic import. Each import that writes anything also writes a `legacy_import.recorded` audit event, holding up to 500 quarantined rows and their total.
   - Projections (`apps/api/src/operations/legacy-projection.ts`) only read. Before the first import they read an empty ledger and do not create the store. A record is projected from its latest import or update event; records the import did not create are not projected.
     - `GET /api/operations/exports/legacy-tracker` returns `{ markdown, records, redactedOmitted }`: the store as an engine-format `applications.md`, ordered by `#`. It always has the #, Date, Company, Role, Score and Status columns, plus any other column a record has. A pipe or line break in a cell becomes a space. Redacted records are left out and counted. When every record came from one column layout, importing the export changes nothing (tested).
     - `GET /api/operations/projections/legacy-tracker` returns `{ records, redacted }`: each imported record's #, id, revision, cells and import time, and the #s of redacted records.
     - `POST /api/operations/projections/legacy-tracker` with `{ markdown, sourceLabel }` returns every application once, by `#`: `imported`, `changed_since_import` (the store's cells plus the tracker's newer `trackerCells`), `not_imported` (only in the text) or `redacted` (no cells), with counts and the quarantined rows. It uses the import planner's own per-row outcomes, so it agrees with what an import would do. A quarantined row counts only through its store record, if it has one.
8. **Backups and restore** (FND-06, `apps/api/src/operations/backups.ts`):
   - `POST /api/operations/backups` writes a consistent copy (`VACUUM INTO`, created owner-only before SQLite writes it) to `operations/backups/operations-<UTC timestamp>.sqlite`, with a `.json` manifest: SHA-256, bytes, schema version, entity and event counts, reason. The manifest holds no record content. `GET /api/operations/backups` lists them without opening the store.
   - `POST /api/operations/backups/:name/restore` with exactly `{ "confirm": true }`. Only a bare name matching the backup pattern is accepted (`404 BACKUP_NOT_FOUND` otherwise, so no path or `..`). The file must match its manifest's SHA-256 (`409 BACKUP_HASH_MISMATCH`), pass SQLite's `integrity_check`, and have this store's schema version, tables and columns (`422 BACKUP_INVALID` with the reason). Only then is the current state backed up (reason `pre_restore`), and every record is replaced from the backup in one transaction on the locked connection, so a restore is all-or-nothing and can itself be undone.
   - Restore on a clean profile: copy a backup and its manifest into `<new data dir>/operations/backups/`, then restore it there.
   - A backup from an older schema version is restored through an owner-only temporary copy beside it, upgraded with the store's migrations and deleted afterwards; the backup file itself never changes. A backup from a newer schema, or one whose upgrade fails, is `422 BACKUP_INVALID` with reason `schema_version`. Backups are not encrypted, and the API never deletes them; a person removes old ones by hand.
9. **Files** are owner-only (`0600`, directory `0700`) where the OS supports it. There is no encryption at rest, consistent with roadmap gap S3.
10. **Deletion and retention** (FND-06): `POST /api/operations/entities/:entityType/:entityId/redact` with exactly `{ id, expectedRevision, confirm: true }` (`RecordRedactionRequestSchema`).
    - Every earlier event of the record keeps its id, type, times, source and revision, but its payload becomes `{}` and it gains `redactedAt` (schema 2 adds the `redacted_at` column). Then one `record.redacted` event is appended, holding only `{ redactedEvents }`, so the record's revision moves on and the redaction is itself in the history. The `id` makes a retry idempotent (`200` with `status: "duplicate"`); a stale revision is `409 STALE_REVISION`, an unknown record `404 RECORD_NOT_FOUND`.
    - The store runs with `PRAGMA secure_delete = ON`, so replaced content is overwritten with zeros inside the file, including overflow pages. After a redaction (and after a restore) the WAL is checkpointed and truncated, so old page versions leave it too. Truncating frees the WAL's disk blocks but does not overwrite them, and SSDs and copy-on-write filesystems may keep old blocks; the store promises only that its own files no longer hold the content. `apps/api/tests/operations-redaction.test.mjs` scans the file and WAL bytes for this.
    - A retry of an already redacted event is matched on everything but its payload and returns the redacted event, so it never fills the payload back in. Reimporting a legacy tracker row whose record was redacted quarantines it as `record_redacted`.
    - Retention: the response's `retention` lists every backup and every pre-migration copy (`operations.sqlite.pre-v<N>-<timestamp>.bak`) that existed at the time, since each was taken before the redaction and may still hold the content, and says that restoring one brings it back. The API does not delete them; the person decides.

## Consequences

**Benefits:** durable, crash-safe, idempotent writes with no new native dependency and no change to the preview package.

**Costs and limits:**
- The API depends on an experimental Node module.
- The store is not safe on network or shared filesystems.
- Nothing is persisted unless `REBOUNDOPS_DATA_DIR` is set; the existing memory-only recovery mode is unchanged.
- A redaction cannot be undone except by restoring a backup taken before it, which brings the content back.
- No feature writes to the store yet. The API opens it lazily, on the first request that appends or lists events (`GET /api/operations/status` only reports, and never opens it), and only when `REBOUNDOPS_DATA_DIR` is set and at least one operations flag is on; a default install never loads `node:sqlite` or creates the file. A second API on the same data directory gets `503 OPERATIONS_STORE_LOCKED`.
- The store tests are part of `npm test`, so CI runs them on Linux (Node 22 and 24) and in the Windows and macOS package smoke jobs (Node 24). On Windows the owner-only permission checks are skipped, because Windows has no POSIX file modes; file permissions there are not verified.
